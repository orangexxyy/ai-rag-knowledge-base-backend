# /agent_demo Minimal Controlled Tool Calling Agent Design

## Task Goal

Design a minimal `POST /agent_demo` endpoint to demonstrate Controlled Tool Calling Agent capability.

This design focuses on one core idea:

- The LLM planner reads the user question and tool schemas.
- The LLM planner returns a structured `tool_call`.
- The backend validates and executes the selected tool through a fixed executor map.
- Dangerous tools require backend authorization and cannot be authorized by the model itself.

This is a design-only step. No `app/`, `frontend/`, `README.md`, `PROJECT_CONTEXT.md`, `test_cases.md`, `evaluation_v2.md`, or business code should be modified in this step.

## Non-Goals

- Do not build a full autonomous Agent.
- Do not build a Multi-Agent system.
- Do not replace `/ask_langchain`.
- Do not change FAISS / BM25 / RRF retrieval behavior.
- Do not change reranker logic or thresholds.
- Do not change semantic router strategy or thresholds.
- Do not change document loader / processor / chunker / index builder / index manager behavior in the design step.
- Do not add arbitrary tool execution.
- Do not allow shell commands, file deletion, git operations, or external APIs in this version.

## Endpoint Design

Request:

```json
{
  "question": "帮我检查知识库状态，如果需要重建就重建。",
  "session_id": "agent_demo_001",
  "allow_rebuild_index": false
}
```

Field meaning:

- `question`: user goal in natural language.
- `session_id`: optional conversation/session identifier, aligned with the existing project style.
- `allow_rebuild_index`: request-level authorization context. It comes from the user / frontend / backend policy, not from the LLM planner.

Important distinction:

- `allow_rebuild_index` is hard authorization context owned by backend request handling.
- `tool_call.arguments.confirm` can be generated by the LLM planner to express that the model believes the user semantically requested `rebuild_index`.
- The model cannot authorize a dangerous operation by generating `confirm=true`.
- Dangerous tool execution requires both model intent and backend authorization.

Response:

```json
{
  "question": "帮我检查知识库状态，如果需要重建就重建。",
  "answer": "已检查知识库状态；当前不允许自动重建索引，因此未执行重建操作。",
  "agent_steps": [
    {
      "step": 1,
      "stage": "tool_call_generation",
      "tool_call": {
        "tool_name": "get_index_info",
        "arguments": {}
      },
      "status": "planned"
    },
    {
      "step": 2,
      "stage": "tool_execution",
      "tool_name": "get_index_info",
      "status": "success",
      "result_summary": {
        "index_exists": true,
        "chunk_count": 128,
        "rebuild_required": false
      }
    }
  ],
  "agent_debug": {
    "agent_type": "controlled_tool_calling_agent_demo",
    "planner": "llm_tool_call_planner",
    "executor_policy": "backend_whitelist_and_schema_validation",
    "allow_rebuild_index": false,
    "dangerous_tool_blocked": false
  }
}
```

## Tool Call Generation

The backend sends the user question and tool schemas to an LLM planner.

Planner input should include:

- user `question`;
- available tool schemas;
- explicit instruction that the LLM must return only a structured `tool_call`;
- explicit instruction that the LLM does not execute tools;
- explicit instruction that dangerous tool authorization is controlled by the backend.
- explicit instruction that output must be strict JSON and must not include natural language outside the JSON object.

The LLM planner returns a structured `tool_call`.

Minimal `tool_call` fields:

- `tool_name`
- `arguments`

Example 1:

```json
{
  "tool_name": "get_index_info",
  "arguments": {}
}
```

Example 2:

```json
{
  "tool_name": "rebuild_index",
  "arguments": {
    "confirm": true
  }
}
```

Key rule:

- The LLM only generates `tool_call`.
- The LLM planner output must be strict JSON and only contain the `tool_call` structure.
- If JSON parsing fails, the backend must return a structured error and must not execute any tool.
- The backend executor performs whitelist validation, argument schema validation, risk checks, and actual execution.
- Prompt constraints are soft constraints. Backend validation is the hard security boundary.
- This demo uses a fixed tool whitelist. In a real enterprise system, the backend can dynamically generate user-visible tool schemas from `user_id`, role, and permission context, then still re-check permissions before executor execution.

## Tool Structure

Each tool must be represented as a structured object:

- `name`: stable tool identifier used in `tool_call.tool_name`.
- `description`: planner-facing explanation of what the tool does and when to use it.
- `parameters_schema`: strict schema for `tool_call.arguments`.
- `risk_level`: `low` or `dangerous`.
- `executor`: backend function that performs the real action.
- `output_format`: expected structured result shape.

The backend should maintain a tool whitelist such as:

```text
get_index_info
search_knowledge_base
rebuild_index
```

Any tool name outside the whitelist must be rejected before execution.

## Tool Design

### Tool 1: get_index_info

- `name`: `get_index_info`
- `description`: Inspect the current knowledge-base index status.
- `parameters_schema`: no parameters, must be an empty object.
- `risk_level`: `low`
- `executor`: backend read-only function that checks loaded index / chunk metadata state.
- `output_format`:

```json
{
  "index_exists": true,
  "chunk_count": 128,
  "rebuild_required": false,
  "knowledge_dir": "data/raw_docs"
}
```

Notes:

- Read-only.
- No file writes.
- No index rebuild.
- Useful for questions like "检查知识库状态".

### Tool 2: search_knowledge_base

- `name`: `search_knowledge_base`
- `description`: Answer a user question using the existing enterprise knowledge-base RAG capability.
- `parameters_schema`:

```json
{
  "question": "string"
}
```

- `risk_level`: `low`
- `executor`: backend wrapper around the existing RAG flow.
- `output_format`:

```json
{
  "answer": "...",
  "retriever_status": "matched",
  "reference_text": "...",
  "used_chunks_debug_summary": []
}
```

Notes:

- This tool wraps existing RAG capability for Agent use.
- It does not replace `/ask_langchain`.
- It should preserve `/ask_langchain` behavior and compatibility.
- Do not copy the full `/ask_langchain` main chain into the Agent route at large scale.
- The first implementation should prefer reusing existing RAG internal capability. If clean reuse is not available yet, return a read-only retrieval summary first to avoid destabilizing `/ask_langchain`.
- If full `reference_text` is too large or sensitive for Agent output, return a concise `used_chunks_debug_summary`.

### Tool 3: rebuild_index

- `name`: `rebuild_index`
- `description`: Rebuild the knowledge-base index when the user explicitly asks for it and backend authorization allows it.
- `parameters_schema`:

```json
{
  "confirm": "boolean"
}
```

- `risk_level`: `dangerous`
- `executor`: backend function that triggers the existing safe index rebuild path after validation.
- `output_format`:

```json
{
  "rebuild_executed": true,
  "status": "success",
  "chunk_count": 128,
  "message": "index rebuilt"
}
```

Notes:

- Dangerous tool.
- Not allowed to execute silently.
- No shell command execution.
- No arbitrary filesystem deletion.
- Must not run unless the double-check rule passes.

## Dangerous Tool Double-Check

`rebuild_index` requires both conditions:

```text
tool_call.arguments.confirm == true
AND
request.allow_rebuild_index == true
```

Blocked example:

```json
{
  "tool_call": {
    "tool_name": "rebuild_index",
    "arguments": {
      "confirm": true
    }
  },
  "request_context": {
    "allow_rebuild_index": false
  },
  "execution_result": {
    "status": "blocked",
    "reason": "dangerous_tool_requires_backend_authorization"
  }
}
```

Meaning:

- `confirm=true` means the LLM planner inferred that the user requested index rebuild.
- `allow_rebuild_index=true` means the backend request context authorizes this dangerous operation.
- The LLM cannot grant `allow_rebuild_index` to itself.
- If either condition is false, the backend must block execution and return a clear blocked result.

## Agent Flow

1. User calls `POST /agent_demo`.
2. Backend reads `question` and request-level authorization context such as `allow_rebuild_index`.
3. Backend sends `question + tool schemas` to the LLM planner.
4. LLM planner returns structured `tool_call`.
5. Backend checks whether `tool_call.tool_name` is in the tool whitelist.
6. Backend validates `tool_call.arguments` against the selected tool schema.
7. If the selected tool is dangerous, backend applies the double-check rule.
8. Backend executes the mapped `executor` only after validation passes.
9. Backend records `agent_steps` for planning, validation, authorization, execution, and result summary.
10. If needed, backend sends the tool result to the LLM to generate the final user-facing `answer`.
11. Backend returns `answer + agent_steps + agent_debug`.

## Safety Rules

- Tool whitelist only.
- No arbitrary code execution.
- No shell command execution.
- No deleting files.
- No git operation.
- No external API in this version, except the existing configured LLM call used for planning / answer generation.
- Dangerous tools require backend authorization.
- Current demo uses a fixed tool whitelist. A real enterprise system may generate visible tool schemas dynamically based on `user_id`, role, and permissions, but executor-side permission checks are still required.
- Prompt constraints are soft constraints.
- Backend validation is the hard security boundary.
- The planner may propose a tool call, but the executor decides whether it can run.
- Tool arguments must be schema-validated before execution.
- Tool execution errors must be caught and returned as structured error results.

## Test Cases

- A001: Query index status.
  - Input asks to inspect knowledge-base status.
  - Expected tool: `get_index_info`.
  - Expected result: read-only status with `index_exists`, `chunk_count`, `rebuild_required`, `knowledge_dir`.

- A002: Query knowledge-base question.
  - Input asks an enterprise policy question.
  - Expected tool: `search_knowledge_base`.
  - Expected result: answer plus `retriever_status` and reference summary.

- A003: Request rebuild with `allow_rebuild_index=false`.
  - Input semantically requests rebuild.
  - Planner may generate `rebuild_index` with `confirm=true`.
  - Expected result: blocked by backend authorization.

- A004: Request rebuild with `allow_rebuild_index=true` and `tool_call.arguments.confirm=true`.
  - Expected result: rebuild executor may run.
  - Expected result should include clear execution status.

- A005: Model generates `confirm=true` but `request.allow_rebuild_index=false`.
  - Expected result: blocked.
  - Confirms the model cannot authorize dangerous operations.

- A006: Unknown tool name.
  - Planner output contains a tool not in whitelist.
  - Expected result: rejected before execution.

- A007: Invalid tool arguments.
  - Example: `rebuild_index` receives `confirm: "yes"` instead of boolean.
  - Expected result: clear schema validation error.

- A008: Tool executor exception.
  - Executor raises an exception.
  - Expected result: API returns structured tool error and does not crash.

- A009: Existing `/ask_langchain` unaffected.
  - Existing normal RAG question still works.
  - Existing low_confidence behavior remains unchanged.
  - Existing session history / memory summary behavior remains unchanged.

## Interview Explanation

- RAG and Agent are different layers.
  - RAG retrieves knowledge and generates an answer from references.
  - Agent decides whether to call a tool, which tool to call, and with what arguments.

- RAG can be one Agent tool.
  - In this design, `search_knowledge_base` wraps existing RAG capability.
  - `/ask_langchain` remains the main RAG endpoint.

- `/agent_demo` is a side-path endpoint.
  - It demonstrates controlled tool calling without destabilizing the main RAG chain.
  - This protects the existing demo API and frontend.

- Tool means `name + description + parameters_schema + executor`.
  - The schema is shown to the model.
  - The executor is backend code and is never controlled directly by the model.

- The LLM only generates `tool_call`.
  - The backend validates and executes.
  - This separation makes the system explainable and safer.

- Dangerous tools need double-check validation.
  - `confirm=true` from the model only means semantic intent.
  - `allow_rebuild_index=true` from the request means backend authorization.
  - Both are required to execute `rebuild_index`.

- `agent_steps` are important for observability.
  - They show what the planner selected, what validation happened, whether execution was blocked, and what result was returned.
  - This is useful for debugging, interviews, and safety explanation.

- This is a controlled tool agent.
  - It is not a complete autonomous Agent.
  - It is not a Multi-Agent system.
  - It is intentionally small, auditable, and safe for a job-search-oriented RAG project.

## Risks And Rollback Notes

- Risk: Planner returns malformed JSON.
  - Mitigation: strict parser and clear validation error.

- Risk: Planner invents a tool.
  - Mitigation: whitelist enforcement.

- Risk: Planner tries to authorize dangerous action.
  - Mitigation: backend-owned `allow_rebuild_index` and double-check rule.

- Risk: `search_knowledge_base` duplicates `/ask_langchain` logic.
  - Mitigation: prefer reusing existing RAG internal capability. If clean reuse is not practical in the first version, return a read-only retrieval summary instead of copying or changing the `/ask_langchain` main chain.

- Rollback:
  - Remove `/agent_demo` router registration and related agent files.
  - Existing `/ask_langchain` should remain unaffected.
